Spec: Swap the AI provider — Claude ⇄ Kimi, as a setting

Make the model provider a runtime setting instead of a hard-wired dependency: route every model call through one dispatcher so the library can run on Moonshot's Kimi (OpenAI-wire-compatible, far cheaper) or Anthropic's Claude, chosen from the Things panel like the existing on-device toggle.

Owns: editor/claude_client.py (the dispatcher), editor/config.py + editor/settings.py (the setting), editor/indexing.py (the batch fallback), editor/blueprints/jobs.py (/api/settings), editor/static/things.js (the picker), editor/requirements.txt.

Parallel: touches the AI seam only. Safe alongside frontend and data specs. Do not run alongside another spec that edits claude_client.py or indexing.py's deep-index jobs.

Why

Every model call in the app currently goes to Anthropic, and the expensive ones — the deep-index pass over sampled frames, rough-cut generation, edit chat — run on an Opus-tier model. Kimi K3 is OpenAI-wire-compatible, carries a 1M-token context, and supports the three things this app actually needs from a model: vision, strict JSON-schema structured output, and prompt caching — at a substantially lower per-token cost. Making the provider a setting means the library can be re-indexed cheaply without giving up the option to run a specific job on Claude.

This is orthogonal to the existing on-device vision toggle. That one decides local CLIP vs. a cloud model; this one decides which cloud model. Both settings coexist: on-device stays free and offline, and the provider setting only applies when a call actually leaves the machine.

What the migration is actually up against

The 2026-07 efficiency pass already did the hard part. Eleven of the twelve model calls now funnel through a single helper, _parse(messages, schema, max_tokens, *, system, thinking, model), so the provider split has one natural seam rather than twelve. What remains is four concrete incompatibilities.

Design

1. The setting

Mirror the existing on-device toggle exactly — env default, DB override, one accessor.

# config.py
AI_PROVIDER_DEFAULT = os.environ.get("AI_PROVIDER", "claude")   # "claude" | "kimi"
MOONSHOT_API_KEY    = os.environ.get("MOONSHOT_API_KEY", "").strip()
MOONSHOT_BASE_URL   = os.environ.get("MOONSHOT_BASE_URL", "https://api.moonshot.ai/v1")
KIMI_MODEL          = os.environ.get("KIMI_MODEL", "kimi-k3")

# settings.py — alongside _use_on_device()
def _ai_provider() -> str:
    """Live provider setting: the stored choice, or the env default if unset."""
    return _get_setting("ai_provider") or AI_PROVIDER_DEFAULT

/api/settings (GET and POST, already in blueprints/jobs.py) gains an ai_provider key. Reject anything that isn't claude or kimi with err(…, 400), and reject kimi when MOONSHOT_API_KEY is empty — a pre-flight check, per the fail-loudly rule, rather than letting the first indexing job die at 3am.

2. The dispatcher

_parse() becomes the fork. Nothing above it changes — the eleven callers keep passing Anthropic-shaped messages and a pydantic schema, and keep receiving a validated model instance.

def _parse(messages, schema, max_tokens, *, system=None, thinking=None, model=None):
    if _ai_provider() == "kimi":
        return _parse_kimi(messages, schema, max_tokens, system=system)
    return _parse_claude(messages, schema, max_tokens,
                         system=system, thinking=thinking, model=model or MODEL)

_parse_kimi() does three mechanical things: translate the message list (images to image_url data URIs, system to a leading message), send response_format={"type":"json_schema","json_schema":{"name":schema.__name__, "schema":schema.model_json_schema(),"strict":True}}, and validate the returned JSON with schema.model_validate(). Keep the translation in one small pure function (_to_openai_messages(messages, system)) so it can be unit-tested without a network call.

Pydantic schemas need a compatibility pass. Strict JSON-schema modes typically require additionalProperties: false and every property listed in required. Several models here use defaulted fields (things: List[str] = [], regions: List[Region] = []). Add a _strict_schema(schema) post-processor that walks model_json_schema() and normalizes it, rather than editing the pydantic classes and changing Claude's behavior too.

3. The batch problem

The deep-index batch job is the one place with no clean Kimi analogue. It exists purely to halve the cost of bulk re-indexing — which is much of the reason to switch providers in the first place, so losing it matters less than it would otherwise.

Recommended: when the provider is Kimi, _run_deep_index_batch_job delegates to the existing synchronous _run_deep_index_job and labels the job "Deep indexing (Kimi, sequential)" so the UI never claims a discount it isn't getting. No new polling machinery, no silent failure. parse_deep_index_json() is already a tolerant, provider-neutral parser and gets reused as-is.

4. The picker

The Things panel already renders the on-device toggle and its status line (#on-device-toggle, #analysis-mode-status in things.js). Add a small provider <select> beside it, wired through the shared api() helper, with a status line naming the active model — e.g. "Kimi K3 · cheaper, 1M context" vs. "Claude Opus · batch discount available". It should read as one coherent "how analysis runs" control group, not two unrelated switches.

Build order

  1. Setting plumbing — config + settings._ai_provider() + /api/settings validation. No behavior change yet; provider stays claude.
  2. Message translation — _to_openai_messages() and _strict_schema() as pure functions, with unit tests over the four vision call shapes. Still no network.
  3. The Kimi path — _parse_kimi() + the _parse() fork. Behind the setting, so claude is untouched.
  4. Batch fallback in indexing.py.
  5. UI picker in things.js.
  6. Live A/B — requires the API key (see blocker).

Steps 1–5 are fully buildable and testable today; only step 6 waits on the account.

Verification

  • Unit — new tests/test_ai_provider.py: the setting round-trips and rejects junk; _to_openai_messages() converts each of the four image-carrying call shapes correctly; _strict_schema() emits additionalProperties:false and full required; _parse() dispatches to the right backend per setting (both mocked).
  • Regression — the whole existing suite must stay green with the provider unset. The conftest AI mocks patch at the claude_client.generate_rough_cut level, so they are already provider-agnostic and should need no changes. If they do, that is a signal the abstraction leaked.
  • Live A/B (needs the key) — deep-index the same 5 clips under each provider and compare scene-segment counts, region counts, and whether watched things are still matched. Then run the real loop end to end on Kimi: assemble → chat revision → export. Record the observed cost delta in the ROADMAP line so the switch is justified by a number, not a vibe.

Risks

RiskMitigation
Quality regression on deep-index or rough-cut, silently degrading the library The A/B above, on real clips, before flipping the default. The setting makes reverting instant.
Strict-schema rejection on the defaulted-list models _strict_schema() normalization + unit tests over every schema in the module.
Losing the batch discount erases the savings on a bulk re-index Measure it in the A/B. Kimi sequential may still beat Claude batch; if not, keep bulk re-indexes on Claude.
Two providers drift as prompts get tuned for one Prompts stay shared and provider-neutral. If a prompt needs per-provider tuning, that is the signal to revisit the single-toggle decision.

Explicitly not in scope

  • Per-feature provider selection (deep-index on Kimi, chat on Claude). Possible later; see the decision note.
  • Streaming responses — nothing in this app streams model output today.
  • Replacing the on-device CLIP/Whisper path. Unrelated and still the cheapest option.
  • A third provider. The dispatcher should not grow a plugin registry for a case that does not exist.

Acceptance

Flipping the Things-panel picker to Kimi and re-running the core loop — import → deep-index → assemble → chat revision → export — produces a working cut with no Anthropic API call made, and flipping back to Claude restores the previous behavior exactly. ./run_tests.sh green in both states.
