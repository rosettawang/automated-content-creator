Why Claude Code (vs. the browser agent)

Going live is terminal work against the local machine: run a resolver check, run the test suite, start the app, read the dry-run payload from logs, toggle env + the arm flag, trigger the publish, and confirm it appeared. Claude Code has the venv, the .env keys, and the shell in reach and can do all of it end to end. A browser-only agent can drive dashboards but has to hand each terminal step back to the user. The single step that stays human in either tool is the final publish confirm — it's public and irreversible.

Runbook (ordered; Claude Code executes 1–7, human presses 8)

  1. Resolver check — confirm the numeric IG id resolves before any real call: 
    cd editor
venv/bin/python -c "
from dotenv import load_dotenv; load_dotenv('.env')
from social.instagram import _resolve_ig_user_id
print('ig_user_id =', _resolve_ig_user_id('ca_xGBSFmzcbfyu'))"
    Expect a long number. If None, dump the connected account and fix _IG_ID_FIELDS in instagram.py.
  2. Tests — ./run_tests.sh from repo root. No commit without it passing.
  3. Start the app (waitress, or FLASK_DEBUG=1 for logs).
  4. Make a photo post in a campaign: an image (hero still or photo clip) + caption. Simplest first post — no video processing.
  5. Dry-run it (SOCIAL_DRY_RUN=1, the default). Read the logged payload and confirm: correct slugs, resolved ig_user_id, image_file = the real path, caption present. Note: dry-run swaps in the DryRun adapter, so it does not exercise the real Composio call or the resolver — step 1 is what de-risks those.
  6. Arm the campaign (POST /api/campaigns/<id>/arm {armed:true}) and set SOCIAL_DRY_RUN=0.
  7. Trigger publish for the one post. Watch it move claimed → publishing → published; capture the returned external_id.
  8. Human confirm (irreversible): the actual public post is confirmed by a person, not automated. After it lands, open Instagram and verify @whrfund shows it.
Safety rails (non-negotiable): post exactly one to start. Never auto-retry a publish that may have gone out — check external_id first. Failures surface on the post (red + error), never a silent log. No app-side deletion of published content. Consider a private/test IG account for the very first fire if one is available; the user has chosen @whrfund directly, so at minimum keep it to one low-stakes post.

Two things to verify on the first live call

  • image_file shape — Composio may want a path string, a {name, content} object, or a file handle. If the container step errors on the media arg, adjust in instagram.py.
  • ig_user_id field name — _resolve_ig_user_id searches common fields; if step 1 returns None, add the real field to _IG_ID_FIELDS.
